## Already there

- `gaia.disk` takes `layout` (the board's `[disk]` table and its in-table `[[partitions]]`, a typed host input) and `partitions` (a fan-in of `gaia:disk-partition`, in port order after the board's).
- `gaia.disk.partition` makes one partition from scalars and an optional `content` image.
- Recipe inputs `build`, `data` and `disk`. `crates/bins/gaia/tests/fixtures/disk` is a working two-partition example.
- Copy conversions, so one image can feed several stages.

## Build

- `recipes/sd-image.toml`: the board's partitions, a bootable root slot A (EROFS + verity, or ext4), an empty slot B of the same size, and a data partition (`data` input, ext4). No board or product names.
- Raw blobs (a boot ROM's first stage and U-Boot at fixed offsets, the board's `[[partitions]]` with `in_table = false`). A CPU node takes one fan-in, and `gaia.disk` spends it on partitions, so blobs need their own node: for example `gaia.disk.blobs(image, blobs: FanIn<RawBlob>) -> Image`, which checks that each blob lies outside every partition and writes it. Their content comes from the board's bootloader build.
- An empty partition (slot B) is a `gaia.disk.partition` with no `content` and a `size`.
