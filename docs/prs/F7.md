## Already there

- `gaia.disk` takes `layout` and `partitions`:
  - `layout` is the board's `[disk]` table and its in-table `[[partitions]]`, as a typed host input.
  - `partitions` is a fan-in of `gaia:disk-partition`, in port order after the board's.
- `gaia.disk.partition` makes one partition from scalars and an optional `content` image.
- Recipe inputs `build`, `data` and `disk`; F8 adds `os`. `crates/bins/gaia/tests/fixtures/disk` is a working two-partition example.
- Copy conversions, so one image can feed several stages.

## Build

- **The slot model.** It has no A/B. A slot is an EROFS image with dm-verity, kept as a file on the ext4 data partition. The disk is:
  - the board's partitions and raw blobs,
  - a boot partition (kernel, device tree, initramfs, boot config) from F8's `os` boot files,
  - the data partition: the image's `data` tree, with the slot file placed in it.
- **Rename** `recipes/ab-slot.toml` to a name without A/B wording, and fix its users.
- **Raw blobs.** These are a boot ROM's first stage and U-Boot at fixed offsets: the board's `[[partitions]]` with `in_table = false`.
  - `gaia.disk.blob(tree, path, name, offset) -> RawBlob` picks a file out of a tree (F8's `os` boot files).
  - A collector `gaia.disk.blobs(FanIn<RawBlob>) -> Vec<RawBlob>` feeds a blobs list port on `gaia.disk`. A CPU node takes one fan-in, and `gaia.disk`'s fan-in is its partitions.
  - `gaia.disk`'s existing layout check keeps each blob outside the table and the partitions.
- No board or product names in the recipe.
