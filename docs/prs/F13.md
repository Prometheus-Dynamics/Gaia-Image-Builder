# F13: A pinned build root

**Group:** F. Recipes, graph, command

**Wave:** 10

**Needs:** F8

**Runs:** cloud

Read `AGENTS.md` and `docs/design.md` first.

## Why

A Rust component's build root is a public image by digest, and its toolchain is the build machine's own sysroot, so the machine must have the right Rust and musl targets installed. A component that compiles C needs a C compiler for the target in the root too. Nobody publishes an image: publishing is an outward action that is the user's, and it puts a moving thing under every build.

## Build

- A recipe that makes a build root from locked inputs, as a tree in the store keyed on them:
  - a base image by digest that has a host C toolchain;
  - the Rust toolchain: the dist archives for the pinned version and the `std` archives for each musl target, each by sha256;
  - a C compiler for the targets, for components that set `cc`, as a locked archive. Take its checksum from the publisher's index and verify the archive's signature; do not take a hash from anyone's message.
- A component names that tree as its `root` (a `root` taken from another output, not only from an image source), and the builder takes the toolchain from inside it. The host-sysroot path goes away.
- An unpack step for the archives.
- If F11 folds the host tools into this root, say so there.
- An example in `examples/`. Real descriptions are Atlas's.

## Proof

Paste: the root built twice in two stores with the same digest; a Rust component built for aarch64, armv7hf and riscv64gc musl on a machine with no Rust installed; a component that compiles C built for the same three.
